# 1. Depend on tokscale-core rather than reimplementing parsing

Date: 2026-09-05

## Status

Accepted

## Context

tokscale reads usage from roughly 50 AI coding clients. Each has its own on-disk
format — JSONL transcripts, SQLite databases, zstd-compressed logs, OTEL exports,
Electron globalStorage blobs — and each has its own quirks around cost provenance,
session identity, and workspace attribution. `tokscale-core` is 110,929 lines of Rust
encoding all of it, plus pricing resolution, model canonicalization, timezone
bucketing, and aggregation.

It is published as an `rlib` and is not on crates.io.

A GUI port needs exactly this data. The alternatives were to reimplement the parsers
in TypeScript, or to shell out to the `tokscale` CLI and consume `--json`.

## Decision

Depend on `tokscale-core` directly as a Rust crate from the Tauri backend, and call it
in-process. Expose the results to the frontend through Tauri commands with TypeScript
types generated by `tauri-specta`.

Reimplementing the parsers is rejected outright: it would mean maintaining a
TypeScript mirror of 50 client formats that change without notice, and any divergence
would show up as silently wrong numbers rather than as an error.

## Consequences

The hardest and most volatile part of tokscale is inherited rather than rewritten.
When upstream adds a client or fixes a parser, the GUI gets it on a version bump.

The GUI's numbers agree with the TUI's by construction, because they are computed by
the same code. This matters more than it sounds: usage figures that disagree between
two views of the same tool are worse than no figures.

Because `tokscale-core` is not on crates.io, the dependency comes from git rather than a
registry.

**Amended 2026-09-05**, following "Research: tauri-specta type generation": the dependency
resolves to the *fork* created under ADR 0002, not to upstream. `#[specta(remote)]` cannot
be used from the GUI crate — both the trait and the types are foreign, so it fails the
orphan rule — which means the `specta::Type` derives must live in `tokscale-core` itself,
behind a cargo feature. The alternative was roughly 150 duplicated DTO fields in the GUI
crate, kept in sync by hand with no compiler check.

Consequently ADR 0002's fork spans both crates rather than `tokscale-cli` alone, and the
conflict surface on upstream merges grows to include any core struct carrying a derive.

The GUI is coupled to `tokscale-core`'s internal API, which carries no stability
guarantee. Upstream refactors will break the build. This is accepted as the cost of not
owning the parsers, and is mitigated by pinning rather than tracking a branch.

**Amended 2026-09-10**, reversing the amendment above. The research was right about the
constraint and wrong about the conclusion. `#[specta(remote)]` does fail the orphan rule
from the GUI crate, but the alternative was never 150 duplicated fields: P1 reads 15. And
core's own shapes are inconsistent in their casing (`ModelUsage` is snake_case, its nested
`ModelPerformance` camelCase), so serializing them directly would export that seam to
TypeScript. The boundary is therefore hand-written DTOs in `src-tauri/src/dto.rs`, uniformly
camelCase because they are declared so in that one module, and no types are generated.

The cost is that `dto.rs` and `src/lib/api.ts` are kept in step by hand, with no compiler
check between them. The DTOs carry about forty fields across the whole boundary, P2
additions included, and at that size the cost is accepted. If P2 grows the surface enough to
want generation, `tauri-specta` can derive from the GUI's own DTOs, which are local types,
so the orphan rule no longer applies and nothing has to move back into core.

The dependency still resolves to the fork rather than upstream, but now only because ADR
0002 forked the repository for its CLI library target, and because the fork makes three
P1 aggregation entry points public. The fork's `specta` feature, which the GUI never
enabled, has been reverted.
